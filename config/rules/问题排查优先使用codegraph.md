# 问题排查优先使用 codegraph

## 1. 适用场景

以下任务**第一步**必须先用 codegraph 检索，再决定是否用 grep / 逐文件阅读：

- 线上问题、Bug、报错排查，根因定位
- 调用链分析：谁调用了 X、X 调用了谁、入口在哪
- 影响面评估：改动某个函数 / 接口会波及哪些代码
- 架构分析：服务耦合、跨服务数据访问、依赖关系梳理
- 陌生模块理解：某个功能在哪实现、关键符号有哪些

不适用：已知文件和行号的精确修改、纯文本或配置检索（如日志关键字、yaml 键）、非代码文件，直接用对应工具。

## 2. 使用前检查（每个会话首次使用时执行一次）

1. 在项目根目录执行 `codegraph status`。
2. 有 Pending Changes → 先执行 `codegraph sync`（增量，通常很快）。
3. 提示"由旧版本构建"或没有索引 → **先告知用户**，由用户决定是否执行 `codegraph index`（全量重建，大仓库耗时较长），不得擅自全量重建。
4. 命令不存在或索引不可用 → 说明原因后降级到 grep / 语义搜索，不阻塞排查。

## 3. 工具选择

有 codegraph MCP 工具时优先用 MCP（如 `codegraph_explore`、`codegraph_node`），否则用 CLI：

| 目的 | 命令 |
|---|---|
| 不确定从哪入手，一次拿到相关符号源码 + 调用路径 | `codegraph explore "<问题描述或关键词>"` |
| 找符号定义 | `codegraph query <名称> [-k function]` |
| 谁调用了它（反向追溯入口） | `codegraph callers <符号> [-f <文件后缀>]` |
| 它调用了谁（正向追踪下游） | `codegraph callees <符号> [-f <文件后缀>]` |
| 改动影响面 | `codegraph impact <符号> [-d 3]` |
| 单个符号源码 + 上下游 / 带行号读文件 | `codegraph node <符号>` 或 `codegraph node -f <文件> --offset N --limit M` |
| 为任务汇总上下文 | `codegraph context "<任务描述>"` |

同名符号多时必须用 `-f` 缩小范围；需要程序化处理结果时加 `-j` 输出 JSON。

## 4. 已知局限（必须规避）

codegraph 是**按名称匹配的静态图谱**，不是类型精确、可达性精确的分析：

- 接口方法、它的多个实现、测试 mock 会混在同一份 callers 结果里。
- 无法判断"函数已定义但从 main / 路由 / 定时任务都不可达"。
- 反射、依赖注入、动态注册（如 `init()` + map、路由表）的调用关系可能缺失。
- 索引可能落后于工作区（未 sync 的改动不可见）。

## 5. 取证要求（强制）

codegraph 只用于**定位线索、缩小范围**，不能直接作为结论：

1. 每条结论必须回到源码确认，并以 `文件:行号` 引用实际代码。
2. 排除 `_test.go`、`*.test.*`、mock、示例代码。
3. 判断"真实使用"时必须追到入口：HTTP / gRPC 路由、消费者、定时任务或 main 启动链路。只有定义、没有可达入口的不算。
4. 区分接口与实现：确认调用方实际注入的是哪个实现（看装配 / 构造处）。
5. Go 项目需要可达性等精确结论时，用 `deadcode`、`go/types` 等工具复核 codegraph 给出的候选。

## 6. 与项目规则的关系

本规则只决定"检索工具的优先顺序"，不替代项目内的排查规范。例如 WorkBuddy 排查仍须先按 `WORKBUDDY-TROUBLESHOOTING.md` 的 Step 0 判定架构归属，再用 codegraph 在对应架构范围内检索。
