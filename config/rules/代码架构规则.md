# 代码架构规则

> 本文件是新项目编码的强制规则。AI 编码和人工开发均须遵循。
> 核心信条：**SOLID 是地基，变与不变分离是骨架；先设计正确，再写代码。**
> 详细示例和领域参考见 references/，本文件只放规则本身。

---

## 0. SOLID 原则（地基）

写任何类、任何接口前先过这五条。

**S 单一职责**：一个类只有一个变更理由。类名能描述其职责（避免 `Manager`/`Helper`）。一个类的所有方法必须围绕同一职责。

**O 开闭原则**：加新变体不应改任何已有代码，只新增文件。`if/else` 或 `switch` 列出类型 = 违反 OCP，改用策略模式 + 注册中心。

**L 里氏替换**：子类不能比父类更严格的前置条件，不能抛出父类不会抛的异常，不能偷改父类的副作用语义。语义不同就改命名/拆接口，不伪装成同一接口。

**I 接口隔离**：实现类不应有"用不到"的方法（空实现/抛 `UnsupportedOperationException` 都是异味）。接口小而专，单一职责。

**D 依赖倒置**：高层模块不依赖低层实现，两者都依赖抽象。内核代码中 import 任何具体变体类 = 违反 DIP，改依赖接口。

> 本规则第 1-7 节是 SOLID 在"多变体服务"场景的具体落地。

---

## 适用范围

**适用本规则**：3+ 变体且共享处理逻辑 ≥ 40%。

**不适用本规则（直接简化）**：

- 变体 ≤ 2 且预期不增长 → 直接 `if/else`
- 逻辑 < 200 行 → 函数级解决
- 变体差异 > 70% → 各自独立实现
- 一次性脚本 → 不抽象

---

## 1. 三层骨架

所有多变体服务按此结构：

```
变体侧（可变）            切分点（边界数据）          稳定内核（不变）
─────────────            ─────────────              ─────────────
策略接口 + 注册中心  ──►  边界数据结构  ──►  无状态单例 + open()→Session
```

设计新服务第一步：填表确定本领域的三层——变体是什么？切分点是什么数据结构？内核处理什么？

> 找不到明确的切分点 = 设计没完成，不要开始写代码。

---

## 2. 变体侧——策略接口 + 注册中心

- 为变体定义统一策略接口（`supportType()` 自报类型 + 业务方法）。
- 注册中心构造器注入 `List<Adapter>`，按 type 路由。
- **新增变体 = 写一个 `implements + @Component`，注册逻辑与内核零改动**（OCP 的标准实现）。
- 注册中心实现因语言而异：Java/Spring 用 `@Component`；Python 用 `entry_points`/装饰器；Go 用 `init()` + map；Rust 用 `inventory`。

---

## 3. 切分点——变体与内核的边界数据结构

- **不可变**：所有字段 `final`、无 setter。
- **自描述**：字段名一眼能懂。
- **可序列化**：未来可能跨服务时，要能 JSON/Proto/Avro 序列化。
- 找不到统一切分点 → 加一层适配（各变体输出 → 统一 DTO），适配层输出即为切分点。

---

## 4. 稳定内核——无状态单例 + Session 隔离

- **单例只持有无状态依赖**（纯函数式组件、DAO、限流器等）。
- **执行状态放 Session，不放实例字段**：`accumulator`、`counter`、`current batch` 等"单次调用状态"必须隔离到 `open()→Session` 的调用方栈上。
- 调用方持 Session：`try (Session s = pipeline.open(ctx)) { s.accept(item); s.flush(); }`。

> **铁律**：单例 Bean 不得在实例字段上存"当前请求/当前批次"状态。并发会互相覆盖。

---

## 5. 命名编码契约

类型名自带约束，让人无法误用：

| 好命名                           | 编码的契约                 |
| -------------------------------- | -------------------------- |
| `BoundedSourceReader`            | 有界，`hasNext()` 必须终止 |
| `StreamIngester`                 | 无界，长驻消费             |
| `SyncNotifier` / `AsyncNotifier` | 同步/异步语义明确          |
| `IdempotentHandler`              | 幂等，重复调用安全         |

| 坏命名                       | 问题                       |
| ---------------------------- | -------------------------- |
| `XxxReader`（实际无界）      | 调用方死锁                 |
| `XxxManager`                 | 职责不清，上帝类           |
| `XxxHandler`（同步异步不明） | 调用方不知道返回后是否完成 |

> 在 Javadoc/Docstring 中钉死前置和后置条件。

---

## 6. 非对称即正确——不强求统一

当变体在生命周期、错误处理、完成语义上本质不同时，让它们的抽象也不同：

- 拉取/订阅需要 source 适配器；推送不需要（数据在请求体）→ 直接复用内核，不设 source 适配器。
- 即时发送（同步）和定时批量（异步）生命周期不同 → 各自独立接口，不强塞同一接口。

> 强行统一 = 把复杂性泄漏进每个实现。非对称不是缺陷，是诚实。

---

## 7. 接口先行，实现延后

不确定的变体：只定义接口，不引入依赖、不写实现。空注册中心正常启动，扩展点就位，零运行时成本。

---

## 8. 测试要求

- **内核必须有并发测试**：多线程压 `accept/flush`，验证状态隔离（每条数据都正确写入，无覆盖）。
- **变体必须有独立单测**：验证"给定输入，产出正确的切分点数据"。
- **切分点数据要有快照测试**：相同输入比对输出 snapshot，确保格式不变。

---

## 9. 分布式场景适配

Session 模式是单进程假设：

| 场景                       | 适配方案                                            |
| -------------------------- | --------------------------------------------------- |
| 微服务拆分（切分点跨网络） | 切分点定义 Proto/Avro 序列化协议                    |
| 消息驱动（状态跨多消息）   | Session 状态外部化（Redis），用 correlation ID 关联 |
| Serverless（无单例复用）   | 改为无状态函数，依赖外部存储                        |

三层骨架不变，状态承载方式按场景调整。

## 10. 目录结构约定

```
xxx-service/
├── adapter/                  ← 变体侧
│   ├── XxxAdapter.java           策略接口
│   ├── XxxRegistry.java          注册中心
│   ├── impl/                     具体变体实现
│   └── model/                    切分点数据结构
├── pipeline/                 ← 稳定内核
│   ├── XxxPipeline.java          无状态单例
│   └── XxxPipelineSession.java   Session
├── test/                     ← 测试（含并发测试）
└── docs/
    └── ARCHITECTURE.md           切分点文档 + 新变体添加指南
```

## 开发前检查清单

**SOLID 基础（5 项）：**

- [ ] 类名能描述职责，每个类只有一个变更理由（S）？
- [ ] 加新变体是否只新增文件、不改已有代码（O）？
- [ ] 子类会否偷改父类副作用语义（L）？
- [ ] 实现类有无被迫实现的"用不到"方法（I）？
- [ ] 内核是否只 `import` 接口/抽象，不依赖具体变体类（D）？

**架构设计（10 项）：**

- [ ] 三层骨架是否确定：变体侧 / 切分点 / 稳定内核？
- [ ] 切分点是否明确、不可变、自描述？
- [ ] 变体是否走策略 + 注册中心？
- [ ] 内核是否无状态，执行状态用 `open()→Session` 隔离？
- [ ] 类型名是否自带契约约束？
- [ ] 语义不同的变体是否独立抽象？
- [ ] 不确定的扩展点是否只留接口？
- [ ] 是否区分"获取/触发"与"处理"？
- [ ] 内核是否有并发测试？
- [ ] 是否产出 `ARCHITECTURE.md`（切分点文档 + 新变体添加指南）？

> SOLID 层未过 = 设计基础有问题，重新设计。
> 架构层未过 = 多变体落地不到位，对照对应章节修正。
> 全部勾选 = 可以开始写代码。
