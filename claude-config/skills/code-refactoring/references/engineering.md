# 工程保障篇 · 测试、发布与回滚详细参考

> 设计正确只是第一步，安全落地才是终点。没有安全网的重构等于裸奔。

---

## 1. 测试安全网（重构前置条件）

### 1.1 三种测试策略（按现有测试情况选择）

| 现状 | 策略 | 动作 |
|------|------|------|
| 有测试且覆盖充分（≥80%） | 确认基线 | 跑一遍确认全绿，进入重构 |
| 有测试但覆盖不足（<80%） | 补齐覆盖 | 补齐重构涉及路径到 80%，再进入重构 |
| 无测试（遗留代码） | 接缝法补特征测试 | 见下方详细流程 |

### 1.2 接缝法（Seam）——无测试遗留代码的解法

参考 Michael Feathers《修改代码艺术》（Working Effectively with Legacy Code）。

**什么是接缝？** 接缝是代码中可以替换行为而不改代码的点。常见接缝类型：

| 接缝类型 | 示例 | 测试时替换方式 |
|---------|------|-------------|
| 依赖注入点 | 构造器参数、setter | 注入 mock/stub |
| 方法重写点 | protected/public 方法 | 子类重写 |
| 静态调用 | `XxxUtil.process()` | 包装成实例方法后注入 mock |
| new 对象 | `new XxxDao()` | 改为构造器注入，再 mock |

**接缝法流程：**

1. **识别接缝**：在遗留代码中找到可以替换行为而不改代码的点。
2. **提取接口**：把依赖（如 `XxxDao`）抽成接口，让原实现 `implements XxxDao`。
3. **改造注入**：把 `new XxxDao()` 改为构造器注入 `XxxDao dao`。
4. **注入测试替身**：在测试中传入 mock/stub，控制返回值。
5. **写特征测试**：固定当前行为——包括 bug 行为。这些测试是回归基线，不是"正确性"测试。

> 特征测试的目的不是验证"正确"，而是固定"现状"——重构后跑一遍，输出必须零差异。

### 1.3 重构期间的测试时间线

```
重构前          重构中          重构后
  │              │              │
  ▼              ▼              ▼
补安全网      每步回归       生产验证
(特征测试     (每步合并前     (Shadow →
 覆盖率≥80%)   跑全量回归)    金丝雀 → 全量)
```

**重构后生产验证三板斧：**

1. **影子流量（Shadow Traffic）**：新旧代码并行跑同一输入，比对输出 diff，确保零差异。不切流量，只比对。
2. **金丝雀发布（Canary）**：5% 流量切新代码，监控错误率、延迟、输出差异。
3. **全量切换**：确认无异常后逐步放量 5% → 25% → 50% → 100%。

## 2. 风险分级与发布策略

### 2.1 风险分级矩阵

| 风险等级 | 特征 | 发布要求 |
|---------|------|---------|
| 低风险 | 纯逻辑提取、无状态、有测试覆盖 | code review + 回归测试 |
| 中风险 | 涉及接口变更、跨模块影响 | code review + 全量回归 + 灰度 |
| 高风险 | 涉及并发状态（Session 模式）、外部 I/O、无测试覆盖 | ADR + 结对 + 灰度 + 回滚预案 |

### 2.2 Feature Flag 灰度发布流程

```
旧实现（线上）          新实现（重构后）
    │                      │
    └── Flag 控制 ────────┘
         │
    ┌────┴────┐
    │         │
  off=旧     on=新
```

**步骤：**

1. 新实现代码上线，但 Feature Flag 默认关闭（流量走旧实现）。
2. **并行运行（Dual Write / Shadow）**：新旧实现同时执行，比对输出，差异率 < 阈值（如 0.01%）。
3. **金丝雀**：5% 流量切新代码，监控 30 分钟。
4. **逐步放量**：5% → 25% → 50% → 100%，每档观察 ≥ 30 分钟。
5. 全量后观察 24-48 小时，确认稳定后可删除旧实现。

### 2.3 回滚预案

| 触发条件 | 阈值示例 | 动作 |
|---------|---------|------|
| 错误率上升 | > 基线 + 0.5% | 关闭 Flag，切回旧实现 |
| 输出差异 | 差异率 > 0.01% | 关闭 Flag，排查 |
| 延迟增加 | P99 > 基线 × 1.5 | 关闭 Flag，排查 |
| 并发异常 | 出现数据错乱/死锁 | 关闭 Flag，排查 Session 模型 |

**回滚操作要求：**
- 操作可在 1 分钟内完成（一键关 Flag）。
- 上线前在预发环境演练一次回滚操作，确认路径畅通。

## 3. 遗留代码与债务处理

### 3.1 重构 vs 包裹的决策树

```
                    改动频率高吗？
                   /            \
                 是              否
                /                \
          逻辑清晰吗？          风险高吗？
          /        \           /      \
        是          否        是        否
        |           |         |         |
      重构     先补测试      包裹      保持现状
               再重构     (Strangler   记录债务
                          Fig)
```

### 3.2 绞杀者模式（Strangler Fig）

当遗留代码风险高、改动频率低时，不重构，而是逐步包裹替换：

1. 在旧系统外层放一个 facade（门面），新功能走新实现，旧功能继续走旧实现。
2. 逐步把旧功能的流量迁移到新实现。
3. 当旧实现流量降为 0，删除旧代码。

> 优点：新旧代码并存，风险可控，随时可回退。

### 3.3 重构期间遇到紧急需求

重构进行中，产品要求紧急修 bug 或加功能——分支冲突如何处理？

| 场景 | 处理方式 |
|------|---------|
| bug 修复影响重构模块 | 在旧代码上修，重构分支 rebase 后合并 bug fix |
| bug 修复不影响重构模块 | 正常修复，与重构并行 |
| 新功能必须加到重构模块 | 采用绞杀者模式，新旧并存，新功能走新实现 |
| 重构周期长 | 缩短每步周期（≤1周/步），每步合并后立即 rebase 业务分支 |

## 4. 团队协作

### 4.1 ADR（架构决策记录）

高风险重构前写 ADR，内容：

- **背景**：为什么需要重构？现状问题是什么？
- **决策**：切分点是什么？采用什么架构？
- **理由**：为什么不选其他方案？
- **风险**：有哪些风险？如何缓解？
- **回滚**：出问题怎么回滚？

ADR 供团队评审，评审通过后才开始动手。

### 4.2 评审清单（给 Reviewer）

| 检查项 | 通过标准 |
|--------|---------|
| 切分点合理性 | 是否有一个明确的边界数据结构？加新变体改动面是否最小？ |
| 内核无状态性 | 单例是否不持有执行状态？状态是否在 Session 中？ |
| 依赖方向 | 内核是否只依赖抽象接口，不依赖具体变体？ |
| 开闭原则 | 新增变体是否只需 @Component，零改动注册逻辑？ |
| 命名契约 | 类型名是否自带约束，能阻止误用？ |
| 测试覆盖 | 重构路径测试覆盖率是否 ≥ 80%？并发测试是否就位？ |
| 回滚预案 | 是否有 Feature Flag？回滚阈值是否定义？ |

### 4.3 重构后交付物

| 交付物 | 内容 |
|--------|------|
| 切分点文档 | 哪个数据结构是切分点，为什么，如何识别 |
| 新变体添加指南 | step-by-step 教程：implements 接口 → @Component → 实现 supportType → 实现 load |
| Reference Implementation | 一个完整的变体实现作为模板 |
| ADR | 架构决策记录（如高风险） |
