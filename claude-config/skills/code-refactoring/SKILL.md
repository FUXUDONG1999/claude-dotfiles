# code-refactoring

本技能提供一套"设计正确 + 工程安全"双闭环的重构方法论。核心理念：**上游可变，内核稳定；
变体可插拔，内核零改动；设计占四成，工程保障占六成——没有安全网的重构等于裸奔。**

详细设计原则、领域示例、检查清单与反模式见 @references/methodology.md。

---

## When to use

当代码出现以下信号之一时触发本技能：

| 信号 | 表现 |
|------|------|
| 类型分支膨胀 | 按类型的 if/else、switch 散落多处，每加一种类型要改一堆分支 |
| 复制粘贴成灾 | 多个类 90% 逻辑相同，只在某一环节不同 |
| 新增=克隆 | 新增一种"XX"=复制整个类再改几行 |
| 职责混杂 | 一个大类里同时塞着"怎么获取/触发"和"怎么处理"两类逻辑 |
| 并发偶发错乱 | 单例服务用实例字段暂存"当前请求"状态，并发下偶发数据错乱 |
| 扩展畏缩 | 想加新渠道/格式却不敢动，因为怕碰核心逻辑 |

> 一句话判断：如果"加一种新的 X"让你害怕而不是兴奋，就该抽象了。

## 适用性判定（先判断再动手）

动手前先过"适用 vs 不适用"决策树——避免对小模块过度工程：

**适用本方法：**
- 变体数量 ≥ 3，或预期会增长到 3+
- 共享内核逻辑占比 ≥ 40%
- 变体间差异集中在"获取/触发/格式"，处理逻辑一致

**不适用本方法（直接简化）：**
- 变体数量 ≤ 2 且预期不增长 → 直接 if/else，不抽象
- 逻辑总量 < 200 行 → 函数级解决，不引入组件
- 变体间差异 > 70%（几乎无共享内核）→ 各自独立实现更清晰
- 一次性脚本 / 定时任务 → 不值得抽象，记录债务即可

**遗留代码特殊判定：**
- 无测试 + 改动频率高 + 逻辑纠缠 → 先补测试安全网，再重构
- 无测试 + 改动频率低 + 风险高 → 用 Strangler Fig 包裹，不重构
- 无测试 + 改动频率低 + 风险低 → 保持现状，记录债务

## Steps

重构分三个阶段执行：**阶段 0（工程前置）→ 阶段 1（设计）→ 阶段 2（工程落地）**。

### 阶段 0：工程前置——建立安全网（不可跳过）

这是整个方法论的安全基础。无安全网不重构。

**步骤 0.1：风险分级**

对重构目标进行风险定级，决定后续步骤的严格程度：

| 风险等级 | 特征 | 要求 |
|---------|------|------|
| 低风险 | 纯逻辑提取、无状态、有测试覆盖 | code review + 回归测试 |
| 中风险 | 涉及接口变更、跨模块影响 | code review + 全量回归 + 灰度 |
| 高风险 | 涉及并发状态（Session 模式）、外部 I/O、无测试覆盖 | ADR + 结对 + 灰度 + 回滚预案 |

**步骤 0.2：测试安全网**

根据现有测试情况选择策略：

- **有测试且覆盖充分**：确认重构涉及路径覆盖率 ≥ 80%，进入阶段 1。
- **有测试但覆盖不足**：补齐重构路径的测试到 80%，再进入阶段 1。
- **无测试（遗留代码）**：执行"接缝法"补特征测试：
  1. 识别接缝（seam）——可替换行为而不改代码的点（依赖注入点、方法重写点）。
  2. 提取接口，让依赖可替换（如把 `new XxxDao()` 改为构造器注入 `XxxDao`）。
  3. 注入测试替身（mock/stub），固定当前行为——包括 bug 行为，作为回归基线。
  4. 特征测试就位后，进入阶段 1。

> 特征测试的目的不是验证"正确"，而是固定"现状"——重构后跑一遍，输出必须零差异。

**步骤 0.3：ADR（架构决策记录，高风险必写）**

重构前写一份 ADR，内容：为什么重构、切分点是什么、预期收益、风险、回滚方案。供团队评审。

### 阶段 1：设计——变与不变分离

**步骤 1：定位切分点**

切分点是变体与内核交接的边界数据结构。找到它就找到了切分线。

切分点发现法：
1. 列出所有变体的输入和输出。
2. 画数据流图，找所有变体输出后、共享处理前的那个数据形态。
3. 如果找不到统一形态 → 需要加一层适配（各变体输出 → 统一 DTO），这层适配的输出就是切分点。
4. 如果切分点有分歧 → 用"新增变体测试"裁决：假设加一个全新变体，按各自的切分点设计，看哪个改动面更小，小的胜出。

参考领域对照表确定本领域的切分点：

| 领域 | 变体（上游） | 切分点（边界数据） | 稳定内核（下游） |
|------|-----------|----------------|-------------|
| 数据采集 | DB / Kafka / HTTP 推送源 | `Map<String,Object>` 行 | 转换 + 配对写入 |
| 通知发送 | 企微 / 邮件 / 短信 / webhook | `RenderedMessage` | 节流 + 发送 + 记录 |
| 支付 | 微信 / 支付宝 / 银行卡 | `PaymentOrder` | 风控 + 记账 + 对账 |
| 文件存储 | COS / OSS / 本地 | `Blob` | 分片 + 断点续传 + 校验 |
| 数据导出 | CSV / Excel / JSON | `DataSet` | 查询 + 分页 + 流式写出 |

> 切分点因领域而异——第一步就是填这张表。

**步骤 2：抽取稳定内核**

把"不变"逻辑抽成：无状态单例 + `open(ctx)→Session` 会话模式。

- 单例只持有无状态依赖（纯函数式组件、DAO 等）。
- 执行状态（累加器、计数器、当前批次）放 Session，由调用方持有，随调用方栈生灭——等价于局部变量，天然线程安全。
- 内核不依赖任何具体变体（依赖倒置）。

> 凡是单例 Bean 需要承载"单次调用状态"的，都用 open()→Session，不要把状态放实例字段。这是并发偶发 bug 的根治之法。

**步骤 3：定义策略接口 + 注册中心**

为变体定义策略接口，用 `supportType()` + Registry 按类型路由：

```
interface XxxAdapter {
    String supportType();      // 自报类型
    Object load(...);          // 变体各自的获取/触发逻辑，产出切分点数据
}

@Component
class XxxRegistry {
    XxxRegistry(List<XxxAdapter> adapters) {  // IoC 自动注入所有实现
        this.map = adapters.stream().collect(toMap(XxxAdapter::supportType, a -> a));
    }
    XxxAdapter get(String type) { ... }
}
```

注册中心实现因语言/框架而异——Python 可用 entry_points 或装饰器注册，Go 可用 init() + map。关键是"按类型路由 + 新增零改动"这个模式本身，不是 IoC 容器。

新增一种变体 = 写一个 implements + @Component，注册逻辑与内核零改动（开闭原则）。

**步骤 4：用命名编码契约**

给接口起自带约束的名字，在 Javadoc 钉死前置/后置条件：
- `BoundedSourceReader`：宣告"有界，hasNext() 必须终止"。
- `StreamIngester`：宣告"无界，长驻消费"。
- `SyncNotifier` vs `AsyncNotifier`：宣告同步/异步语义。

> 命名是最廉价的文档。当一个名字能阻止下一个人误用，抽象就成功了。

**步骤 5：设计线程模型**

确认单例 vs 执行状态。但凡单例要承载单次调用状态，就用 `open()→Session` 隔离到调用方栈。**必须写并发测试用例**（多线程压 accept/flush），不能靠"想一下"。

**步骤 6：保持接口级，实现延后**

不确定的变体只留接口，不引入依赖、不写实现。空注册中心（注入空 List）在 Spring 下正常启动，扩展点就位，零运行时成本。

**步骤 7：审查非对称性**

检查是否有变体被强行塞进不适配的抽象。语义本质不同就让它独立：
- 采集器：拉取/订阅需要 source 适配器（主动连源），推送不需要（数据在请求体，被动接收）。
- 通知：即时发送（同步）与定时批量（异步）生命周期不同，不必硬塞一个接口。

> 强行统一 = 把复杂性泄漏进每个实现。非对称不是缺陷，是诚实。

**贯穿原则：保持行为等价**

每步重构后验证可观测行为不变。先抽离、再优化，不要边抽象边改语义。验证方法见步骤 0.2 的特征测试。

### 阶段 2：工程落地——安全发布与回滚

**步骤 8：Feature Flag + 灰度发布**

重构后的新实现用 flag 控制，不直接替换旧实现：

1. **并行运行（Dual Write / Shadow）**：新旧实现同时执行，比对输出，差异率 < 阈值（如 0.01%）才进入下一步。
2. **金丝雀发布**：5% 流量切新代码，监控错误率、延迟、输出差异。
3. **逐步放量**：5% → 25% → 50% → 100%，每档观察 ≥ 30 分钟。

> 分布式场景注意：Session 模式是单节点假设。跨服务时切分点数据需定义序列化协议（Proto/Avro）并考虑 schema 演进；跨消息时 Session 状态需外部化（Redis/DB），用 correlation ID 关联。

**步骤 9：回滚预案**

上线前定义回滚标准和演练回滚操作：

- **触发回滚的条件**：错误率 > X%、输出差异率 > Y%、延迟增加 > Z%。提前定好阈值。
- **回滚操作**：关闭 Feature Flag，流量切回旧实现。确保操作可在 1 分钟内完成。
- **回滚演练**：上线前先在预发环境演练一次回滚，确认路径畅通。

> 如果重构期间切分点选错——发现边界数据结构不够用——立即止损。停下，回步骤 1 重新找切分点。已完成的代码作为"领域知识"保留（加深了对系统的理解），但不保留错误设计。前两次切分点选错是正常的，第三第四次才收敛。

**步骤 10：分支策略与团队协作**

- **每步一个可独立合并的 PR**：步骤 1（分析，产出表格无代码）、步骤 2（一个 PR，只搬移不改逻辑）、步骤 3（一个 PR，引入接口+注册中心+迁移第一个变体）。
- **重构分支短生命周期**：建议 ≤ 1 周/步，每步合并后立即 rebase 业务分支。
- **重构期间遇到紧急需求**：采用绞杀者模式逐步替换，新旧代码并存，流量逐步迁移。
- **高风险步骤结对进行**：步骤 1（识别切分点）和步骤 2（抽取内核）建议结对编程。
- **重构后交付物**：除代码外，产出切分点文档、新变体添加指南（step-by-step）、一个 reference implementation 作为模板。

## Pitfalls

| 反模式 | 问题 | 正解 |
|--------|------|------|
| 起模糊名字塞错语义 | `XxxReader` 却承载无界流，hasNext() 永不终止 | 命名编码契约（Bounded/Stream） |
| 单例把执行状态放实例字段 | 并发调用互相覆盖，偶发数据错乱 | open()→Session，状态上栈 |
| 给所有变体强套同一策略接口 | 语义不同的变体被强行统一 | 非对称即正确，该独立则独立 |
| 抽象时引入未来才用的依赖 | 污染当前构建、增加维护面 | 接口先行，实现/依赖延后 |
| 边抽象边改语义 | 引入隐蔽 bug，难以定位 | 先抽离保行为等价，再单独优化 |
| 用 List 全量加载替代迭代器 | 大数据量 OOM | 流式迭代器，常量内存 |
| 内核反向依赖具体变体 | 加变体要改内核，开闭原则失效 | 内核只依赖抽象接口 |
| 把"获取"和"处理"混在一个大类 | 类膨胀、难测试、难复用 | 切分点切开，获取=变体侧，处理=内核侧 |
| **无测试安全网就重构** | 重构后无法验证行为等价 | 步骤 0 先补特征测试，覆盖率 ≥ 80% |
| **无回滚预案就上线** | 出问题无法止损 | 步骤 8-9 先建 Feature Flag + 回滚演练 |
| **切分点选错硬撑** | 边界数据结构不够用，越改越乱 | 止损回步骤 1 重新定位 |
| **小模块过度抽象** | 3 个变体 50 行代码上策略+注册+Session | 参照适用性判定，≤2 变体直接 if/else |

## Verification

重构完成后逐条对照检查清单：

### 设计层检查
- [ ] 是否找到了"变与不变"的切分点（一个明确的边界数据结构）？
- [ ] 稳定内核是否独立成组件，不依赖任何具体变体（依赖倒置）？
- [ ] 变体是否走策略 + 注册中心，新增变体零改动注册逻辑（开闭原则）？
- [ ] 类型名是否自带契约约束，能阻止误用？
- [ ] 单例 Bean 的执行状态是否通过 open()→Session 隔离，而非实例字段？
- [ ] 并发场景是否有测试用例验证（多请求/任务同时执行互不干扰）？
- [ ] 语义不同的变体是否被强行统一了？该独立的是否独立了？
- [ ] 不确定的扩展点是否只留接口、未引入多余依赖？
- [ ] 重构前后可观测行为是否等价？
- [ ] 是否区分了"怎么获取/触发"与"怎么处理"，不让它们混在一个类里？

### 工程层检查
- [ ] 重构前是否建立了测试安全网（特征测试覆盖率 ≥ 80%）？
- [ ] 高风险重构是否写了 ADR 并通过团队评审？
- [ ] 是否定义了风险分级（低/中/高）并匹配对应的发布策略？
- [ ] 新实现是否用 Feature Flag 控制，可一键切回旧实现？
- [ ] 是否执行了并行运行（Shadow）验证输出差异率 < 阈值？
- [ ] 是否定义了回滚触发条件（错误率/差异率/延迟阈值）？
- [ ] 是否在上线前演练了回滚操作？
- [ ] 重构期间每步是否保持一个可独立合并的 PR？
- [ ] 重构后是否产出了切分点文档和新变体添加指南？
- [ ] 团队是否对新模式有共识（不止重构者一人理解）？

> 全部勾选 = 重构安全完成。设计层有未勾选项 = 回对应步骤修正。工程层有未勾选项 = 不要上线。
